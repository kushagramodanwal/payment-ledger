# PostgreSQL setup (fresh database)

This backend now uses PostgreSQL through `pg` and does not migrate or import any MongoDB data.

## 1. Create a database

If PostgreSQL is installed locally and its service is running:

```bash
createdb wallet
```

Alternatively, create a database named `wallet` in pgAdmin or your PostgreSQL provider.

## 2. Configure environment variables

From the `backend` directory:

```bash
cp .env.example .env
```

Edit `.env` and set `DATABASE_URL` to your database connection string and `JWT_SECRET` to a long random secret. Example for local PostgreSQL:

```env
DATABASE_URL=postgresql://postgres:YOUR_PASSWORD@localhost:5432/wallet
JWT_SECRET=replace_with_a_long_random_secret
JWT_EXPIRE_MINUTES=30
PORT=8000
INITIAL_BALANCE_INR=10000
PG_POOL_MAX=20
PG_SSL=false
```

Do not commit `.env` or share its secrets. Set `PG_SSL=true` only if your hosted PostgreSQL provider requires TLS. For providers with custom certificate requirements, use their recommended SSL configuration instead of disabling certificate verification in production.

## 3. Create the tables

Run from the `backend` directory, replacing the connection string with your actual one:

```bash
psql "postgresql://postgres:YOUR_PASSWORD@localhost:5432/wallet" -f src/config/schema.sql
```

The schema creates `users`, `wallets`, and `transactions`, along with constraints and transaction-history indexes. It is intended for a fresh database. It does not copy data from MongoDB.

## 4. Install dependencies and run

```bash
npm install
npm run dev
```

The backend starts on port `8000` by default. Check it with:

```bash
curl http://localhost:8000/health
```

## Notes

- User, wallet, and transaction IDs are generated by PostgreSQL identity columns.
- Money is stored as integer paise (`BIGINT`) to avoid floating-point storage for currency.
- Signup creates the user and wallet in one database transaction.
- Transfers lock both wallet rows in a consistent order and update both balances plus the transaction record in a single PostgreSQL transaction.
- Idempotency keys are stored as UUIDs and remain unique.
- This is a fresh-database migration. Do not point the application at a production database until you have reviewed the schema, configuration, and application behavior.
